## Current Install Flow

`install_statusline` (setup.sh:1052-1480) contains an inner function `_run_install_statusline_for_target(target_config_dir, mode)` that is called twice at the bottom: once for global mode and once for project mode, depending on flags.

The flow inside `_run_install_statusline_for_target` has two distinct phases:

### Phase 1 — settings.json gate (lines 1068-1117)

Detects whether a `statusLine` key already exists in `settings.local.json` OR `settings.json` (in that order). Sets `has_statusline=true` and `found_in=<path>` if found.

**Already-installed branch (lines 1088-1103):**
```
if [ "$has_statusline" = true ]; then
  if [ "$FORCE" = true ]; then
    # overwrite silently
  else
    echo "  [warn] Existing statusLine config found in ${found_in}"
    if [ ! -t 0 ]; then return; fi          # non-interactive: skip
    printf "  Existing statusLine detected. Overwrite with CMM statusline? [y/N] "
    read -r overwrite_reply
    case "$overwrite_reply" in
      y|Y) ;;
      *) echo "  [skip] Statusline installation skipped"; return ;;
    esac
  fi
fi
```

This prompt is only about whether to overwrite the `statusLine` key in settings. It says nothing about the component options. After the user answers `y`, execution falls through to Phase 2.

### Phase 2 — component config gate (lines 1119-1185)

Computes `sl_config_path` based on mode:
- **project mode:** `~/.cache/codebase-memory-mcp/_statusline-config-<md5_of_pwd>.json`
- **global mode:** `~/.cache/codebase-memory-mcp/_statusline-config-default.json`

Then:
```
if [ -f "$sl_config_path" ] && [ "$RECONFIGURE_STATUSLINE" = false ]; then
  echo "  [info] Statusline config found: ${sl_config_path}"
  # *** skips all prompts — goes straight to writing scripts ***
else
  # show interactive prompts
fi
```

**This is the bug.** When the statusline is already installed (Phase 1 detects it) AND the `_statusline-config-*.json` file already exists, Phase 2 silently skips all component prompts. The user never gets to change their component selection. Re-prompting only happens if `--reconfigure-statusline` is explicitly passed.

### Phase 3 — script generation and settings write (lines 1187+)

Generates `.claude/hooks/statusline-cmm.sh` (global: standalone, project: wrapper) and merges `statusLine.command` into `settings.local.json`. This always overwrites the script file regardless of whether Phase 2 re-prompted.

## Option Set

The interactive component prompts (shown when `sl_config_path` does not exist or `--reconfigure-statusline` is set) ask about exactly 6 boolean keys, all defaulting to `true` (press Enter = yes):

| Key | Prompt text | Display output |
|-----|-------------|----------------|
| `cmm_total` | Show CMM total (CMM:N)? [Y/n] | `CMM:<total>` |
| `cmm_details` | Show CMM details (sg:X cs:Y tr:Z)? [Y/n] | `(sg:N cs:N tr:N)` |
| `blocks_total` | Show Blocks total (Blk:N)? [Y/n] | `Blk:<sum>` |
| `block_details` | Show Block details (R:X/B:Y)? [Y/n] | `Blk:RN/BN` |
| `ctx_total` | Show Context Mode total (CTX:N)? [Y/n] | `CTX:<total>` |
| `ctx_details` | Show Context Mode details (ex:X bex:Y sr:Z)? [Y/n] | `(ex:N bex:N sr:N)` |

The non-interactive/`--yes` path writes all six as `true` (hardcoded defaults).

Note: The `statusline_hide_limits`, `statusline_hide_agent_in_tmux`, etc. keys in `.vbw-planning/config.json` are VBW plugin config, not CMM statusline config. They are unrelated to this phase.

## Current Default Source

Current values live entirely in `sl_config_path`:
- `~/.cache/codebase-memory-mcp/_statusline-config-<project-hash>.json` (project mode)
- `~/.cache/codebase-memory-mcp/_statusline-config-default.json` (global mode)

These are external to the repo and to `.claude/`. They are the only source of truth for current selections. The generated `statusline-cmm.sh` script reads them at runtime via `jq`. Nothing is baked into the script itself at install time.

The project hash is `md5(pwd -P)` computed at install time (line 1124-1126). At runtime in `statusline-cmm.sh`, the hash is computed from `git rev-parse --show-toplevel` (walking superprojects). These two computations can diverge for monorepos or worktrees — but that is a pre-existing issue, not new.

## Re-prompt Design Notes

### (a) Detect already-installed

Two independent already-installed signals exist:

1. **`has_statusline=true`** — `statusLine` key present in settings file (Phase 1). This is the "settings are configured" signal.
2. **`sl_config_path` exists** — the component config JSON is present (Phase 2). This is the "options were previously chosen" signal.

For the re-prompt, both can be true at once (normal re-run), or only the config file can exist (settings were wiped), or only settings can exist (cache dir was cleared). The most useful case is both present.

### (b) Extract current values

Before showing the re-prompt, read existing values from `sl_config_path` using python3 or jq. Example:

```bash
local cur_cmm_total cur_cmm_details cur_blocks_total cur_block_details cur_ctx_total cur_ctx_details
cur_cmm_total=$(python3 -c "import json; d=json.load(open('$sl_config_path')); print('true' if d.get('cmm_total', True) else 'false')" 2>/dev/null || echo true)
# ... same for remaining 5 keys
```

### (c) Offer re-prompt with pre-selected defaults

Currently every prompt is hard-coded to `[Y/n]` (default yes). To show the current value as the default:

- If current value is `true` → show `[Y/n]` (unchanged behavior).
- If current value is `false` → show `[y/N]` (default no).

The `read -r` response is already processed correctly: empty/Enter → treat as default. No structural change needed to the `case` block; only the `printf` hint string needs to be dynamic.

```bash
local yn_cmm_total
[ "$cur_cmm_total" = "true" ] && yn_cmm_total="Y/n" || yn_cmm_total="y/N"
printf "    Show CMM total (CMM:N)? [%s] " "$yn_cmm_total"
read -r sl_cmm_total
case "$sl_cmm_total" in
  n|N) sl_cmm_total=false ;;
  y|Y) sl_cmm_total=true ;;
  "")  sl_cmm_total=$cur_cmm_total ;;  # Enter → keep current
  *)   sl_cmm_total=$cur_cmm_total ;;
esac
```

The empty-string case (`""`) must be added — currently `*` catches Enter and maps it to `true`. That needs to become: Enter → inherit current default.

### (d) Trigger condition change

Currently: Phase 2 skips prompts when `sl_config_path` exists AND `RECONFIGURE_STATUSLINE=false`.

New behavior: when the statusline is **already installed** (`has_statusline=true`) AND `sl_config_path` exists AND running `--project` interactively, **always** re-prompt with current values as defaults, unless `--yes`/non-interactive.

This means replacing:
```bash
if [ -f "$sl_config_path" ] && [ "$RECONFIGURE_STATUSLINE" = false ]; then
  echo "  [info] Statusline config found: ${sl_config_path}"
else
  # prompts
fi
```

With:
```bash
if [ -f "$sl_config_path" ] && [ "$RECONFIGURE_STATUSLINE" = false ] \
    && [ "$has_statusline" = false ]; then
  # First-time install where config already exists (edge case) — skip
  echo "  [info] Statusline config found: ${sl_config_path}"
elif [ "$YES_FLAG" = true ] || [ ! -t 0 ]; then
  # Non-interactive: write defaults
  ...
else
  # Read existing values, show re-prompt with current defaults
  ...
fi
```

Or more simply: **always show the component prompts when interactive, reading current values as defaults.** The `sl_config_path` existence check's primary purpose was performance (skip unnecessary prompts on first-time non-already-installed runs). It can be dropped for the already-installed path.

### (e) Write back

No change needed. The existing `cat > "$sl_config_path" <<SLCFG` heredoc at the end of the interactive branch already writes all 6 keys. It will overwrite with the new values.

## Unknowns / REQUIRES LIVE VALIDATION

1. **Project-hash computation consistency.** The install-time hash uses `pwd -P` (line 1124). The generated script uses `git rev-parse --show-toplevel` at runtime. For a freshly-cloned project these match; for a symlinked or worktree path they may not. Not new, but re-prompting writes to the install-time hash path, which is correct.

2. **`--reconfigure-statusline` flag fate.** The new behavior (always re-prompt when already-installed + interactive) makes `--reconfigure-statusline` partially redundant for the already-installed case. Decision needed: keep it as a way to force re-prompt even when `has_statusline=false` (i.e., settings wiped but config exists), or deprecate. Recommendation: keep it — it handles the edge case where settings were wiped.

3. **`SKIP_CONTEXT_MODE` flag interaction.** No interaction — statusline install is independent of context-mode install.

4. ⚠ REQUIRES LIVE VALIDATION — Confirm `_statusline-config-<hash>.json` is written to `~/.cache/codebase-memory-mcp/` (not `.cache/` relative to CWD) in all modes. The `$HOME` prefix is present in the source but should be verified with an actual `--project` run.

5. **`--force` flag and re-prompt.** With `--force`, Phase 1 skips the "Overwrite?" question and proceeds. Phase 2 currently still skips prompts (config-exists guard fires before the FORCE check). Under the new design, `--force` should probably also force re-prompt — or `--force` can be treated as `--reconfigure-statusline` automatically. Needs a decision.
